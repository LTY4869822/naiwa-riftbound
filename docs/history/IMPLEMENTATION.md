## 第一个原型要回答的问题

“喂食带来的角色成长，能否在下一场战斗中被玩家立即感知，从而愿意重复这个循环？”

先做独立、可丢弃的交互原型验证这个问题。原型只使用虚拟数据碎片，不操作真实文件；人物和场景允许占位。桌宠窗口兼容性作为另一个独立小实验验证，避免把玩法是否有趣与 Windows 窗口问题混在一起。

继续的信号：玩家能看懂同一角色的等级变化，并在下一次战斗中主动使用新能力。若喂食与战斗完全脱节，则先调整反馈和奖励设计，再扩大地图或美术内容。验证结果需要真实试玩，不能由源码检查代替。

## 目标结构

```text
一个 Godot 进程
  ├─ CharacterState：等级、经验、已解锁技能、外观、材料
  ├─ ProfileStore：唯一存档写入者，版本与备份
  ├─ ModeController
  │    ├─ Battle：普通窗口，2D 横版战斗
  │    └─ DesktopPet：人物范围的小透明置顶窗口
  ├─ CharacterVisual：两种模式共享图集和动作映射
  └─ FeedingService
       ├─ SimulatedProvider：原型阶段的虚拟碎片
       └─ FileProvider：后续人工选取、预览、暂存与恢复
```

CharacterState 使用 Autoload 持有，界面通过状态变更信号刷新。战斗和桌宠不分别维护两个等级文件；两者是同一个角色的表现模式。技能效果参数和图集信息使用独立资源配置。

## 实施顺序与验收

| 阶段 | 工作 | 验收标准 |
|---|---|---|
| A：玩法闭环原型 | 一个角色、一个竞技场、一种敌人；移动、跳、攻击、受击；虚拟喂食；等级和技能反馈 | 喂食前后有可观察的技能变化；关卡能胜败和重试；此阶段不接真实文件 |
| B：桌宠技术实验 | 小透明无框置顶窗，待机、散步、拖拽、进入战斗和返回 | 角色外区域不会拦截大面积桌面；拖拽/松开正常；窗口不会丢出工作区；可正常退出 |
| C：共享成长与本地存档 | 角色 ID、技能、等级、外观一致；单写入服务 | 两种模式即时一致；重启恢复；坏档能提示并读取备份；重复奖励事件不重复发放 |
| D：真实文件喂食 | 显式选取少量普通文件，预览路径/数量/大小，可恢复暂存 | 取消无副作用；失败不发奖励；成功有清单；恢复冲突不覆盖；中途退出后能恢复操作状态 |
| E：动作内容与清理能力扩展 | 连招、第二种敌人、Boss、正式角色；再评估垃圾候选规则 | 战斗可独立成长；文件处理不成为唯一升级途径；系统缓存适配逐类验证后才增加 |

阶段 A 的动作可借鉴《断帧》的短输入缓冲、前摇/有效帧/后摇、命中停顿和击退；按自身游戏重新实现。不要将其公开素材当成已有许可素材。

## 文件喂食的产品行为

用户主动选择文件 → 看到操作预览 → 确认交给角色 → 实际文件操作成功 → 播放吞噬动画 → 记一笔奖励 → 战斗读取新状态。

首版不通过扩展名或“长时间未用”就认定一个文件无价值。先支持用户明确挑选的少量本地普通文件；系统目录、程序目录、网络盘、目录递归及重解析点均不进入首版处理范围。路径和实际文件身份需在操作时重新校验，不能只相信预览时的数据。

可恢复暂存先使用应用管理的同卷目录及操作清单，避免将回收站调用当作可恢复性保证。跨卷移动留到后续实现复制校验及失败回滚后支持。暂存仍占磁盘空间，应显示“已暂存可恢复大小”，不能写成“已释放空间”。永久移除属于独立清理步骤，不能藏在吞噬动画之后。

移动前写计划、移动后记录实际结果；异常重启时逐项核实。恢复时遇到同名文件须另存或让用户选择，不直接覆盖。批次 ID 与奖励记录绑定；失败项、取消和重复提交不能重复计奖。文件操作与存档不能假定具备数据库式原子性，需要恢复流程。

真实文件处理至少测试：锁定文件、权限拒绝、重命名后选择失效、同名恢复冲突、断电/中止、重复按钮事件。测试只在专用可丢弃样本目录进行。

## 成长设计起点

战斗本身提供主要经验；喂食提供少量材料、装饰或每日有限加成。奖励不与删除字节数无限正相关，避免制造大文件刷数值。玩家无需清理自己的重要文件也能正常推进。

初次喂食应带来一个容易感知的收益，例如获得一次可选技能强化或外观变化；只显示微小攻击数字增加不利于验证玩法。正式平衡数值在原型试玩后再定。

## 不纳入第一版的内容

多角色、多地图、联网账号、云存档、AI 聊天、全盘自动清理、后台自动删除、内存加速宣传、多人对战及其他应用窗口攀爬。它们不影响先验证同角色跨模式成长。

## 后续工程的验证边界

建议 Windows / Godot 4.7.2 / GDScript / Compatibility，实施时固定引擎和参考仓库版本。先检验主透明窗口，再导入战斗基础；示例能启动不等于目标版本兼容或整款游戏可玩。

工程应先做场景引用检查、Godot 导入/脚本检查，再做本机窗口与输入实测。只有真实运行、看到完整循环后，才可标记为“可玩原型”。暂不宣称任何帧率、内存占用或打包大小。
